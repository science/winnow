# Winnow — Developer Guide

Working notes for picking up feature work in this repo (written agent-to-agent; humans welcome). `CLAUDE.md` carries the binding rules; `docs/DESIGN.md` carries the architecture and the *why*; this file carries the *how*: where things live, what breaks when you're careless, and the recipes for common changes.

## Orientation (read in this order)

1. `CLAUDE.md` — house rules (auto-loaded). TDD red/green, test tiers, commit discipline are not optional.
2. `docs/DESIGN.md` — architecture, data flow, storage schema registry, product non-negotiables.
3. This file.
4. `QUESTIONS.md` — open user-blocked items; check before building on an unverified seam.
5. `git log --oneline -15` — recent history is phase-structured and readable.

Status as of 2026-07-14: MVP confirmed working by the user against real YouTube data and real provider scoring. CI green on `main`.

## Data flow (one refresh, end to end)

`Feed.svelte` onMount → `initFeed()` loads stored videos/watched (refetch if TTL-stale) → `refresh()` → `loadFeeds()` fetches `/feed/subscriptions` + `/` with session cookies via `ytPage.fetchFeedPage` → `feedParser.parseFeedPage` → merged/deduped `Video[]` into `feedStore.videos` + storage → `scoreFeed()` → strategy branch: **two-phase** (default) runs `runTwoPhaseScoring` (cached digests → transcript pass → enrich misses → translate profile → pure rank, scores land at once); **direct** does cache check against `profileHash(profile, PROMPT_VERSION, modelId)` → misses enriched with transcripts (cap 60) → `runScoring` batches of 20 at concurrency 2 → scores persist per batch and stream into `feedStore.scores`. Either way `tiers` derived re-buckets.

Demo mode (`?demo=1`) short-circuits: fixture videos, deterministic stub scorer, zero network. All nonlive e2e runs this path.

## Invariants and gotchas

Things that WILL bite if forgotten:

- **`PROMPT_VERSION` must be bumped for any change to the system prompt, schema, or user-message shape.** It's a profileHash input; forgetting it serves stale cached scores produced by a different prompt. Model ID constants are also hash inputs, so swapping a model self-invalidates.
- **Strict structured-output schemas reject numeric bounds and optional fields.** Scores are clamped client-side in `runScoring`; keep `additionalProperties: false`; for OpenAI strict mode every field is required (nullable-then-canonicalize if optionality is ever needed).
- **Retry taxonomy is a house rule:** one 2s retry on 429/5xx/network only; 4xx and malformed JSON fail fast (they're bugs); 401 aborts the run and banners.
- **`feedParser.ts` never throws.** A malformed item is skipped, never fatal. Every recognized shape has a fixture test. Don't widen the parse surface casually.
- **Store pattern (wolfechat):** init from storage, then `subscribe → persist`, gated by a `persist` flag so the initial default write doesn't clobber stored state before load. Copy `settingsStore.ts` when adding a store. Svelte 5 runes are for component-local state only; anything cross-component or persisted is a store.
- **`isConfigured` requires a key for the *selected* provider.** `applyKeyChange` re-points the provider at whichever key exists — keep that invariant or onboarding silently deadlocks (this was the first real-user bug).
- **A subscribed channel is boosted, never exempted.** `applyChannelBoost` adds a modest lift, but `capped` makes the cap (45) win outright — following a creator must not drag their off-profile videos in front of the fold, or "avoid X" stops meaning anything the moment you follow someone who sometimes does X. Locked by tests at both the unit and `runTwoPhaseScoring` level; the subscribed set is in both score hashes (sorted, so iteration order can't churn them).
- **`substanceDensity` is NOT a quality veto, and re-adding it will winnow honest content.** It is genre-correlated, not garbage-correlated: live music, performance, and trailers legitimately score 1-2 because they are not informational. Measured on the real capture, vetoing `sub<=2` winnowed 46% of the feed (KEXP sessions, a Stewart Copeland drum performance, the Dune trailer). Only `clickbaitSeverity`/`claimOverreach >= 4` veto — that is the pre-existing `CLICKBAIT_FLAG_THRESHOLD`, deliberately reused instead of adding a second threshold. Off-profile content is the topic axis's job, not the veto's. See `docs/CUT_SCORE_RANKING.md` §4.
- **The topic weight floor is a RATIO, and that is the point.** `TOPIC_WEIGHT_FLOOR_RATIO` (0.7 x numeric-axis weight) keeps an off-profile video's ceiling at ~73 against the Top-picks threshold of 75 — for *any* weight mix. The translator emits materially different importances between runs on identical input (§5), so an absolute floor would silently stop guaranteeing anything. Invariant: production quality alone reaches the top of Worth-a-look, never Top picks. Applied only when the profile names topics; with an empty seek list it would amplify a constraint that does not exist.
- **Winnow does not write to the YouTube account unless `Settings.accountWrites` is on, and requests no `cookies` permission.** The switch (default off) is the one gate for anything that changes account state; today it only swaps the player to the signed-in `youtube.com/embed` (see docs/DESIGN.md → Privacy for why that player is signed in and what is still unverified). Put any future write behind it. Credentialed reads ride the browser's own session (`credentials: "include"` under the host permission); no code reads a cookie value. `src/lib/manifestVersion.test.ts` fails the build if `cookies` reappears in the manifest. The subscribe write built on 2026-07-31 (SAPISIDHASH-signed POST, `subscribe.ts` + `authCookies.ts` + `sapisidHash.ts`) was pulled back out before the 0.2.3 listing pending UAT — restore it with a revert of the removal commit, and treat it as a product decision: it re-adds a permission (every installed copy is disabled until the user re-accepts), needs AMO re-review, and changes `PRIVACY.md` and `docs/store/AMO_LISTING.md`.
- **Feedback is deliberately NOT a cache-key input, in EITHER engine.** Votes never invalidate cached scores; they ride in prompts for future cache misses, and "Re-score everything" is the feed-wide apply. Hashing feedback would full-re-score on every click. Two-phase used to violate this (votes were in `targetInputHashFor`), which meant every vote re-ran the translator — and the translator returns a materially different target between runs on identical input, so a single vote could drop an axis and reshuffle the feed. It is now write-behind: votes accumulate, and a pending set is folded in when `FEEDBACK_FLUSH_NEW_FRACTION` of the feed is content never digested before (a day-or-two gap; a 30-minute gap returns nearly the same feed) or on an explicit `requestFeedbackFlush()`. Do not put feedback back in either hash. The voted video itself moves tiers instantly via `bucketVideos`' vote override (a user vote outranks the score AND the clickbait demotion).
- **Profile suggestions apply only on explicit user approval** ("suggested, never silent" — product rule). Apply routes through a normal `profile.update`, so the re-score falls out of the hash change.
- **Demo scorer is deterministic by design** (fnv1a of videoId). Nonlive e2e asserts exact tier placements (`abc123DEF45` → top, `live456GHI78` → winnowed). Changing its math means recomputing those expectations. Two deliberate e2e seams: ids prefixed `unvet` never get a demo score (exercises the awaiting-vetting fold), and `?slow=1` alongside `?demo=1` delays each demo batch so in-progress scoring states are observable.
- **Unvetted videos never render as browsable feed items.** While a run is active the feed shows a progress panel (`scoring-progress`); leftovers a run couldn't score sit behind the `unvetted-fold` (with Retry inside). Don't reintroduce an always-visible unscored section.
- **While a player is open the feed order is frozen.** `playerStore` snapshots the tiers on open and renders them through `freezeTiers`; `Feed.svelte` subscribes to `route` with a plain subscription (NOT an `$effect`, which runs after the DOM update and is therefore too late). Moving an `<iframe>` in the DOM reloads it, so a watched mark, a vote, or a scoring run finishing would otherwise destroy playback mid-video. Held ids resolve against every live tier, so a video that changed tier stays visually put; the release lands on close.
- **Player telemetry is listen-only, origin-filtered, and poll-driven.** `enablejsapi=1` is paired with `origin=location.origin` because the extension-tier gate measured that the player answers ONLY the page's own origin — the DNR referer value and an omitted origin both produce total silence. Winnow never sends the player a command, and the `message` listener hard-filters on `event.source` AND `event.origin`. Two measured gotchas, both caught by `e2e/extension/playerTelemetry.test.mjs` and locked by unit tests: the player answers `listening` polls rather than pushing on its own (stop polling and the position freezes at the first sample), and its `infoDelivery` updates are PARTIAL — the duration arrives once and later samples carry `currentTime` alone, so `updatePositions` carries the last known duration forward.
- **`#/watch/<id>` is not a page, it IS the open-player state.** The hash is the single representation of what's playing — Back closes, deep links work, and one-video-at-a-time is structural rather than enforced. An id that isn't in the feed window (a bookmark, or the `jNQXAC9IVRw` the ext/live tiers deep-link) renders a standalone player above the status chain, so it never waits on feed loading.
- **The player embed only works because a DNR rule injects a Referer.** YouTube rejects embed requests with no HTTP `Referer` (player error 153), and Firefox never sends one from `moz-extension://` pages. `embedRefererRules` (lib/embed.ts) sets `Referer: https://winnow.misuse.org/` on embed sub-frame requests from both player hosts, registered at runtime by `embedRefererReady` as a **dynamic** rule with `initiatorDomains: [<this install's moz-extension host>, "www.youtube.com"]`. The second initiator is load-bearing: once youtube.com has installed its service worker (every real YouTube user's profile — a fresh test profile has none), Firefox re-issues the signed-in player's navigation with `www.youtube.com` as the initiator, and without it every signed-in play is error 153 (found in the user's browser 2026-09-16; a `tabIds`-scoped session rule does not match the re-issued request). Embeds on other sites keep their own initiator and register no partitioned service worker, so they stay untouched — the ext tier checks both after visiting youtube.com. It must stay dynamic and scoped: the host is random per install so a static rule can't name it, and the old unscoped static rule (measured 2026-09-16) also rewrote the Referer of embeds on every website the user visited. `manifest.json` carries the `declarativeNetRequestWithHostAccess` permission and both host permissions for it; `public/dnr-rules.json` now holds only the InnerTube Origin rule, and a unit test forbids a Referer rule there. Tests that build their own iframe must `waitForEmbedRefererRule` first (the player awaits registration; a bare iframe races it into error 153). Do NOT "simplify" the referer to a youtube.com URL — YouTube rejects its own domain with error 152. Unit tests (`src/lib/embed.test.ts`) lock the wiring; `e2e/live/embed.spec.ts` pins the contract against real YouTube (route-`fetch`+`fulfill`, because browsers ignore `route.continue` Referer overrides on iframe navigations); `npm run test:e2e:ext` installs the built zip into REAL headless Firefox (selenium + geckodriver — Playwright can't load Firefox extensions) and asserts the player is playable from a genuine `moz-extension://` origin. Run the ext tier after any change to the manifest, DNR rules, or embed markup. As of Firefox 153 / geckodriver 0.37 Marionette refuses `driver.get("moz-extension://…")` outright, so that tier opens its pages through the browser's chrome context with the system principal (`e2e/extension/driver.mjs#openExtensionPage`, which is why geckodriver runs with `--allow-system-access` — geckodriver 0.37.1 rejects the older `-remote-allow-system-access` Firefox argument). `e2e/extension/accountWrites.test.mjs` proves the signed-in player sees the unpartitioned youtube.com jar (a planted marker cookie stands in for a sign-in) and that the Referer rule leaves other sites' embeds alone. In chrome-context network observers, read request headers at `http-on-examine-response`: `http-on-modify-request` observers can run before DNR's rewrite. Debugging an installed extension needs `npm run build:dev`. Extension-page console is plain F12 on the winnow tab; background script via `about:debugging` → Inspect.
- **Demo mode never touches `browser.storage.local`.** `lib/storage.ts` routes every `?demo=1` read/write to the page's own localStorage, in the extension too. Before 2026-09-16 it didn't: opening demo mode in the user's installed extension replaced their cached feed with the fixtures, and the refresh pruned their watched marks, resume points, and transcript/digest caches down to the fixture ids. `e2e/extension/demoIsolation.test.mjs` guards it; extension-tier tests that inspect demo state read `localStorage`. Never drive demo mode in someone's real profile expecting it to be harmless without this guard.
- **Live e2e seeds `winnow:videos:v1` with a fresh `fetchedAt`** so `initFeed` stays inside the TTL and never touches YouTube — that's how real-provider scoring is testable in a plain browser. Keys come from gitignored `.env.production`; never bake keys into a build (non-`VITE_`-prefixed vars can't leak into the bundle, keep it that way).
- **VM/host split:** build in the VM, load `~/dev/winnow/dist/manifest.json` on either side's Firefox via `about:debugging`; dev servers bind `0.0.0.0`; never run git from host and VM simultaneously.

## Recipes

1. **New pure logic** — RED unit test in `src/lib/*.test.ts` first, minimal GREEN, refactor. If the logic wants browser APIs, split: pure part in `lib/`, thin adapter in `services/`.
2. **Parser breakage / new YouTube shape** — get a real capture (user: Settings → "Copy debug fixture"), prune it to the minimal reproducing structure, drop it in `src/services/youtube/fixtures/`, write the failing fixture test (`should parse <shape>` / `should skip <junk>`), then extend `feedParser.ts`. Never fix the parser without a fixture locking the shape. **Raw captures are signed-in and carry session/account identifiers — always run them through `npx vite-node scripts/scrub-capture.ts <in> <out>` before committing** (it refuses to write while `scanSuspectKeys` flags anything; big captures get gzipped, committed as `.json.gz`, with the unzipped name gitignored — see `gotham-poor-ranking-capture.json.gz` and `captureFixture.test.ts`).
3. **New provider** — implement `ScoreBatchFn` in a new `<name>Scorer.ts` with a single model constant; throw `ProviderError` with the right `kind`; add a stub for unit tests; wire the adapter/model switch in `scorer.ts#scoreFeed`, the `Provider` union in `types.ts`, and the Settings radio. Add a live e2e case. The model constant joins the cache hash automatically.
4. **New setting** — field in `types.ts#Settings` + `DEFAULT_SETTINGS` (spread-merge on load keeps old stored blobs valid) + a control in `Settings.svelte` (`onchange` → `settings.update`). Persistence is free via the store subscription.
5. **New persisted key** — add to `KEYS` in `storage.ts` with a `:v1` suffix, register in DESIGN.md's schema table, access only through `storageGet/Set/Remove`. Schema change later = new `:v2` key + migration read, not silent shape drift.
6. **New UI behavior** — `data-testid` on the element, helper in `e2e/helpers/` (locator preference: `getByLabel` → `getByRole` → `data-testid` → CSS), spec in `e2e/nonlive/` through helpers only. If it needs scored videos, demo mode provides them deterministically.
7. **Prompt/scoring-quality change** — edit `prompt.ts`, **bump `PROMPT_VERSION`**, update scorer unit tests, then run `npm run test:e2e:live` (costs cents) to prove both providers still parse and the substance-vs-bait directional assertion holds.

## Verification loop

```bash
npm run check && npm test     # after every change — fast, free
npm run test:e2e              # builds + demo-mode Playwright; before commit
npm run test:e2e:live         # real provider calls; when touching prompt/providers/scorer
```

Manual smoke when the change affects real-YouTube behavior: `npm run build` (or `build:dev` for logs), reload the temporary add-on, refresh, compare against youtube.com. Before every commit: `git status` and account for every file. CI red on `main` is stop-the-line.

**Releases (AMO listed channel):** Winnow is published on addons.mozilla.org. `v*` tags build and attach two artifacts to the GitHub Release: the extension zip (`npm run zip`) and the source zip for AMO's reviewers (`npm run source-zip` — tracked files from HEAD, includes `BUILD.md`; refuses a dirty tree). Submission itself is manual: Developer Hub → Upload New Version → channel "On this site" → extension zip, then the source zip when asked about bundlers; listing copy lives in `docs/store/AMO_LISTING.md`. **Version numbers are unique across BOTH AMO channels and a seen version is never re-signable** — bump `package.json` AND `public/manifest.json` together before tagging (`src/lib/manifestVersion.test.ts` keeps them in sync). `npm run sign` (unlisted channel, credentials in gitignored `credentials/env.production`) remains only for deliberate self-distributed builds — never on a version number intended for the listing.

### Release checklist

**The Dev Hub uploads from local disk, not from GitHub.** Whatever sits in `web-ext-artifacts/` is what gets submitted, so a release is not "done" when CI is green — it is done when the CI-built artifacts are on this machine. Steps 3 and 4 exist because a stale local zip is indistinguishable from the right one in the file picker.

1. **Bump** `package.json` + `public/manifest.json` to the new version (one commit), push, wait for green CI on `main`.
2. **Tag** `git tag -a vX.Y.Z -m "…" && git push origin vX.Y.Z`. CI builds both zips and attaches them to the GitHub Release.
3. **Pull the artifacts down before uploading anything** — `gh release download vX.Y.Z -p "winnow-X.Y.Z*.zip" --clobber` into `web-ext-artifacts/`, overwriting whatever is there. Never upload a locally built zip: every build stamps the current commit into the page footer (`__GIT_HASH__`), so a zip built before the release commits carries a hash that no longer matches the source zip a reviewer rebuilds from. Same code, different bytes, failed reproducibility check.
4. **Verify the pair reproduces**, from the downloaded files, not the working tree: unzip the source zip to a temp dir, `npm ci && npm run build`, `diff -r` its `dist/` against the unzipped extension zip. Clean diff or do not submit.
5. **Upload** at the Dev Hub: channel "On this site", the extension zip, then **answer "yes" to the code-generator/bundler/minifier question and attach the source zip** — Vite (rollup + esbuild minify), the Svelte compiler, and Tailwind all qualify, so source is mandatory, not optional. Paste "Notes to reviewer" and the version notes from `docs/store/AMO_LISTING.md`.
6. **Confirm what actually landed** — `node scripts/amo-status.mjs` (read-only AMO API call, credentials from the gitignored `credentials/env.production`). It prints each version's channel, permissions, whether **source is attached**, and whether reviewer notes are non-empty. `source: null` on a listed version means the submission is incomplete regardless of what the automated review said.


For pure UI iteration, skip the extension loop entirely: `npm run dev` → `http://<vm>:5173/feed.html?demo=1`.

## Debugging playbook

- **Feed empty or missing videos** → warnings banner under the refresh row shows per-feed parse failures; Settings → "Copy debug fixture" exports the raw `ytInitialData` that produced them (also in `ytPage.lastCaptures`).
- **Scoring silently does nothing** → `scoreFeed` no-ops when unconfigured: check provider/key pairing and profile text (`missingConfig` logic). In a `build:dev` build the console shows batch retries and the `transcripts: N/M fetched` line (with a per-stage failure breakdown, also rendered under the feed header).
- **Inspect stored state** → extension: F12 on the winnow tab → `await browser.storage.local.get(null)`. Plain browser/e2e: `localStorage` with the same `winnow:*` keys.
- **Score cache confusion** → compare `winnow:scores:v1`.profileHash against `profileHash(profile, PROMPT_VERSION, model)`; a mismatch means the whole cache is intentionally dead. Settings → "Re-score everything" nukes it.
